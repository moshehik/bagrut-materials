# Project notes (site: חומרים לבגרות)

## Stack
- Next.js (App Router) + TypeScript. See the auto-generated block above (from AGENTS.md) — the installed Next.js version has API/convention differences from training data; check `node_modules/next/dist/docs/` before writing framework-level code.
- DB: Drizzle ORM over Neon (serverless Postgres). Schema in `src/db/schema.ts`, client in `src/db/index.ts` (lazy proxy client with a fetch timeout so a DB hiccup can't hang a server render).
- Curriculum taxonomy (categories tree) is managed by `scripts/curriculum-tree.ts` + `scripts/seed.ts` (idempotent, tracked). Run via the `db:seed` npm script. `scripts/verify-tree.ts` sanity-checks the seeded tree.

## Two unrelated "content" pipelines — do not conflate them
1. **Catalog/category tree** (`scripts/curriculum-tree.ts`, `scripts/seed.ts`): structural metadata only — subjects/units/categories that materials attach to. Clean, tracked, safe to edit like normal app code.
2. **Lesson-material authoring** (ad-hoc, mostly NOT tracked in git): hand-writing the actual downloadable `.docx`/PDF study sheets (enrichment pages, quizzes, teacher sheets). Workflow: dump a source `.docx` to XML/text → cache relevant Sefaria API lookups as scratch JSON → hand-write the Hebrew content into a one-off build script → inject back into `.docx` via JSZip → export PDF. Finished deliverables live in `/חומרים מוכנים מחדש/` (gitignored on purpose — not part of the site's source).
   - Scratch/working files for this workflow (dump scripts, cached JSON, `_render_temp_ch*/` folders, etc.) are gitignored via the `_*`/`_tmp*`/`_render_temp_ch*/` patterns in `.gitignore`. **Keep using that naming convention** (prefix throwaway root-level scratch files with `_`) so they stay out of `git status` and out of routine project-wide scans.
   - `/חומרים מוכנים מחדש/` has zero git history/backup by design (gitignored) — **except two files, tracked on purpose since 2026-09-14**: `הוראות לבניית כל החומרים החדשים/כל ההוראות לבניית החומרים.md` and `הוראות לבניית כל החומרים החדשים/יומן תיקונים מבני (סטטוס קבצים).md` (see `.gitignore`'s negation rules for the exact pattern — everything else in that subfolder, and the rest of the tree, stays ignored). Don't assume anything else under this folder (docx/PDF deliverables, scratch/cache JSON) is recoverable from git.
   - **The local file here is NOT what the live site serves — never assume editing it fixes a live download/preview.** Materials are served per-row from the `materials` DB table: `file_url` is either `drive://<fileId>` (fetched live from Google Drive via `driveDownload()` in [driveBridgeCore.ts](src/lib/driveBridgeCore.ts) — most `draft`-status materials) or (old dead rows only) a Vercel Blob URL — **Vercel Blob is cancelled entirely: no code, no dependency, no token; those rows return "not found" and can only be revived by re-uploading to Drive** (see [docs/drive-storage.md](docs/drive-storage.md)). `fetchFile()` in [file-source.ts](src/lib/file-source.ts) reads Drive only. Nothing reads this local folder. To actually ship a content fix: find the material's `id`/`file_url` in the DB, and if it's `drive://<fileId>`, re-upload the corrected local file to that **same** `fileId` via Drive API `PATCH /upload/drive/v3/files/{fileId}?uploadType=media` (not a new file — keeps the DB row valid, no DB write needed). Back up the live Drive content first. Then verify end-to-end by replaying the site's actual flow (Drive download → zip-path normalize → Oracle convert), not just by checking the local file. Full worked example (incl. how to get a Drive token via the same Apps Script bridge the site uses) in `כל ההוראות לבניית החומרים.md`, entry dated 2026-09-14 ("הבחנה קריטית לתיקון כל חומר קיים").
   - **Bulk local→Drive→site sync (2026-10-05):** the Drive archive is a folder tree mirroring the site's category tree, and `drive-sync` only attaches files already sitting in it — a finished local docx that was never put in its category folder simply doesn't exist on the site. Run `npx tsx scripts/sync-local-materials-to-drive.ts --plan` after any build/fix round (read-only: new / same / replace / drive-newer per file; category from the local path via `scripts/local-category-resolver.cjs`), then `--apply` (uploads as `draft`, replaces content in place with a local backup, never deletes). Verify with `scripts/verify-local-drive-sync.ts`. Beware: `adoptFiles`/`placeMaterial` take `withFolderLock` — never call them from inside the same folder's lock (silent deadlock, Node exits 0). Details + first-run numbers: [docs/drive-storage.md](docs/drive-storage.md).
   - Cached Sefaria/source lookups (verses, Rashi, gemara, midrash) are indexed at `חומרים מוכנים מחדש/_מקורות-מטמון/אינדקס.md` — check there before re-fetching a source, and add a row when caching a new one.
   - Corrections/instructions from the teacher are tracked two ways: full history+reasoning in `חומרים מוכנים מחדש/הוראות לבניית כל החומרים החדשים/כל ההוראות לבניית החומרים.md`, and a lean structured status ledger (which files already incorporate which correction #) in `יומן תיקונים מבני (סטטוס קבצים).md` in that same folder — update both when a new correction comes in, but only the ledger needs re-reading for a "which files still need this fix" sweep.
   - **Fill-in-the-blank lines: always use literal underscore characters (`____`), never spaces-with-underline-formatting (`<w:u/>` on a run of `" "` chars).** Confirmed bug (2026-09-14, "פרק כ" materials): a run of only spaces with underline formatting silently loses its underline when it lands at a line-wrap boundary in the exported PDF (the renderer trims trailing whitespace there) — the blank line just vanishes, mid-sentence, with no visual trace. Underscore characters are real glyphs and don't get trimmed, so they always render regardless of where the line wraps.

All mail goes `sendMail()` ([mail.ts](src/lib/mail.ts)) → POST to `MAIL_SCRIPT_URL` (.env, .env.local, Vercel ×3 envs; Vercel needs a Redeploy after a change). Since 2026-10-05 it points at its **own** Apps Script project in the new "לו״ז העניין" Gmail (deployment ending `…QnvA5w`), a copy of the shared "מערכת מייל פתוח" script that also serves gemach-app.
- The sender **address** = the account that runs the deployment (Execute as: Me); the sender **name** comes from `senderName` (= `MAIL_FROM_NAME` or `SITE_NAME`). Without `senderName` the shared script falls back to 'גמ"ח שמלות'.
- Update a deployment (New version) only from the new account — an update from another account moves "Me" to it. Don't edit the shared "מערכת מייל פתוח" project without the owner's explicit OK.
- The Drive bridge (`DRIVE_BRIDGE_URL`, ending `…JTfa`) is a completely different script — don't touch it when changing mail.
- Repo is public: never commit a full `/exec` URL (anyone holding it can send mail from the account).

## Netfree — all file transfer must go through our own domain

Many students/teachers browse through Netfree (a content-filtering proxy common in the Charedi sector) which only lets the browser talk to the site's own domain — a direct request to a third-party host (`drive.google.com`, etc.) is blocked outright. This is a hard constraint on the whole file-transfer design, not an edge case:
- **Downloads**: never link directly to Drive. Every material download goes through `GET /api/download/[id]` ([route.ts](src/app/api/download/[id]/route.ts)), which fetches the file server-side (via `fetchFile()`/`driveDownload()`) and streams it back from our own domain, watermarking it on the way.
- **Uploads**: same reasoning in reverse — a direct browser `PUT` to `vercel.com` is blocked, so admin uploads go in ≤4MB chunks through `POST /api/admin/upload/chunk` (see the comment at the top of [upload-form.tsx](src/components/admin/upload-form.tsx) and [chunk/route.ts](src/app/api/admin/upload/chunk/route.ts)); each chunk is staged in Google Drive (`archive_append` — there is no Vercel Blob any more) and `/finish` merges them into one Drive file stored as `drive://<fileId>`. Details: [docs/drive-storage.md](docs/drive-storage.md).

## Deploying the live site (code) — `git push` deploys (repo is public, like gemach-app)

Since 2026-10-04 the repo `moshehik/bagrut-materials` is **public**, exactly like `gemach-app`. (Before that it was private, and on Vercel's Hobby plan a private repo only deploys commits authored by the team owner; the GitHub login is linked to a second Vercel user, so every push was **Blocked** with `TEAM_ACCESS_REQUIRED` from ~2026-09-22. Public repos are exempt from that check.) Because the repo is public: **never commit secrets** (`.env*` are ignored; keep it that way), and there is no default admin password in `scripts/seed.ts`.

- **Normal flow**: commit + `git push origin main` → Vercel builds and deploys production automatically. Verify with `npx vercel ls bagrut-materials --scope team_ktg14QXUIxVh6dPLI5awK0Vw` (NODE_OPTIONS=--use-system-ca): newest row must be `Ready`, not `Blocked`.
- **Fallback / immediate**: `/deploy` or `powershell -ExecutionPolicy Bypass -File scripts\deploy-site.ps1 -Message "<what changed>"` (typecheck, commit allowlisted paths, push, clean export, `vercel deploy --prod --archive=tgz`, verify). Use it if a push ever shows `Blocked` again. `.github/workflows/deploy-vercel.yml` is a second fallback (needs a `VERCEL_TOKEN` secret; inert without it).
- New tables/columns in `src/db/schema.ts` must exist in Neon **before** pushing (`db:push` is broken here — use raw SQL like `scripts/create-fix-tables.ts`), because a push now deploys immediately.
- This is unrelated to lesson-material uploads (docx/PDF → Drive/DB), covered below.

If a feature ever needs to hand the browser a file URL, it must be a same-origin route, never a raw third-party URL — otherwise it silently breaks for every Netfree-filtered visitor with no client-side error to debug from.

## Two computers — which folder to run from

This repo is worked on from two physical Windows machines, both sometimes running Claude Code sessions on it at once. **Figure out which machine you're on before touching git**: run `$env:COMPUTERNAME` (PowerShell) or `echo $COMPUTERNAME` (bash).

- **Hostname `משה`** (this machine has a battery / is a laptop, chassis type "Notebook", model `82H8`): work from **`C:\dev\bagrut-materials`** — a real local clone of `github.com/moshehik/bagrut-materials`. **Do not** run git commands from `G:\מחשבים אחרים\המחשב הנייד שלי\Desktop\אתר חומרים לבגרות` — that path is a Google Drive "other computers" remote view of the *other* machine's disk, not a local clone. Running git there produced verified `.git/objects` corruption (`git fsck` — bad-sha1 loose objects) on 2026-09-14, recovered by a fresh clone into `C:\dev`. The old `G:\...` copy still exists for reference only; don't commit/push/merge from it again.
- **The other machine** (labeled `המחשב הנייד שלי` in this Google account's Drive "other computers" list — its own real hostname wasn't identified, no direct access to query it): keeps working from its own local disk copy exactly as before. One thing worth checking there too: if that repo's folder sits inside a path Drive is backing up on *that* machine (e.g. under its own Desktop/Documents), the same kind of interference is possible in principle, just one-directional (upload) instead of the two-directional remote-view case above.
- **Golden rule for both machines:** the only supported way to move work between them is `git push` / `git pull` against GitHub (`origin` = `https://github.com/moshehik/bagrut-materials.git`). Never rely on Drive (or any generic file-sync tool) to carry `.git` state between machines — it doesn't understand git's object model and will silently corrupt it under concurrent writes, as happened here.
